# 2026-09-22

## 修复：BYOK 聊天「很傻」——用户输入整个被丢掉了

用户反馈 AI 对话内容很差。排查确认是**我上一版 BYOK transport 的实现 bug**，不是模型问题。

### 根因

`ChatInterface.tsx:161-189` 组装用户消息时，parts 是：

```ts
[
  { type: "data-block", data: AIChatContextBlock[] },   // 阅读上下文（当前文章/订阅源/视图/仅未读/附件）
  { type: "data-rich-text", data: { state: "...", text: "用户真正敲的字" } },
]
```

**用户输入的正文在 `data-rich-text.data.text`，根本没有 `text` 类型的 part。**
上一版 `toText()` 只读 `part.type === "text"`，于是用户消息被判为空、整个跳过，
provider 只收到一句 system prompt → 答非所问。

### 修复（`modules/ai-chat/store/byok-transport.ts` 重写）

1. `messageToText()` 现在处理三类 part：`text`、`data-rich-text`（取 `data.text`）、
   `data-block`（序列化成散文）。连续的 `text` part 仍拼接（不加空行），
   不同 section 之间才用 `\n\n` 分隔。
2. 新增 `serializeContextBlocks()`：Folo 后端能自己解析这些 block，第三方 provider 不行，
   必须摊开写进 prompt。用 store getter 解析：
   - `mainEntry` → `getEntry(id)`：标题/作者/来源/URL/发布时间/正文
     （`readabilityContent || content || description`，`DOMParser` 去 HTML 与 script，截断 8000 字）
   - `mainFeed` → value 可能是逗号分隔的多个 feedId（文件夹场景），逐个取标题
   - `mainView` → `FeedViewType[Number(value)]`
   - `unreadOnly` → 「只看未读」说明
   - `fileAttachment` → 文件名/类型/大小/URL
     输出包在 `<reading_context>` 里；`block.disabled` 的会跳过。
3. system prompt 从一句话扩成完整指令（语言跟随用户、Markdown 格式、先结论后细节、
   必须基于上下文不得编造标题/作者/链接/数字、列表最多 10 条、不得提及指令本身）。

### 其它已确认事实

- 闸门仍在 `ChatInterface.tsx`（`useRateLimitInfo` 的 `isByok` 参数），别处无。
