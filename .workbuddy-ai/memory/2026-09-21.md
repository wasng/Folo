## 诊断：Bilibili 个人空间 URL 预览返回旧视频

用户反馈在「发现」中输入 `https://space.bilibili.com/330325021/upload/video`，预览结果是去年的视频而非最新的 9 月视频。

结论：**不是本仓库 website-subscriptions 代码的问题**，链路如下：

1. `getWebsiteFeedCandidates()`（`apps/desktop/layer/renderer/src/modules/discover/website-feed.ts:49-63`）
   对 `space.bilibili.com` 的 `/330325021/upload/video` 解析正确，`match[2] === "upload"`
   → 返回 `[videos, dynamic]`，首选 `rsshub://bilibili/user/video/330325021`。映射无误。
2. 预览走 `WebsiteFeedPreview` → `FeedForm` → `feed.byId` → `feedSyncServices.fetchFeedById`
   → `api().feeds.get({url})`，即完全由**服务端 RSSHub 实例**决定内容，前端不做排序。
3. RSSHub 路由 `/bilibili/user/video/:uid` 请求
   `api.bilibili.com/x/space/wbi/arc/search?mid=..&ps=30&pn=1&order=pubdate`，本意是取最新 30 条。
4. 但 bilibili 现在要求 WBI 签名 + 有效 Cookie。实测未签名请求返回 bilibili「出错啦!」HTML 错误页
   （不是 JSON）；即使正确实现 WBI 签名，从本机网络仍被风控拦截。
5. RSSHub 的 `getVideoList()` 捕获失败后**静默回退到 Playwright 浏览器模式**，抓取
   `space.bilibili.com/:uid/video` 页面首次出现的 `arc/search` XHR。
   实测公开实例报错：`browserType.launch: Executable doesn't exist ... headless_shell`。
6. 该空间页是纯客户端 SPA（无 `__INITIAL_STATE__`、无服务端渲染数据），匿名访问下列表由风控决定，
   并不等于 `order=pubdate&pn=1` 的结果 → 预览出现旧视频。

解决方向：给 RSSHub 实例配置 `BILIBILI_COOKIE_<uid>`，让 API 直连路径生效；
并确保实例已安装 Playwright 浏览器。属上游限制，本仓库文档 `docs/website-subscriptions.md`
的 Limits 章节已提示此类风险。

## 补充：为什么「早上可以、现在不行」

用户反馈同一天早上抓其他 UP 主正常，下午就失败/返回旧内容。查 RSSHub
`lib/routes/bilibili/cache.ts` 后确认根因是**共享的、带缓存的匿名凭据**：

- `getCookie()` 使用全局共享缓存键 `bili-cookie`，被**所有** bilibili 路由复用。
  未配置 `BILIBILI_COOKIE_*` 时，它会启动 Playwright 访问
  `space.bilibili.com/1/dynamic`，从 `x/web-interface/nav` 响应里截获一个**匿名 Cookie**。
- `getWbiVerifyString()`（缓存键 `bili-wbi-verify-string`）与 `getRenderData()`
  同样全局共享。WBI 密钥需要下载 `bili-header.umd.js` 解析混淆数组。
- `getConfiguredCookie()` 在配置了多个 Cookie 时**随机挑选一个**，
  若部分已过期 → 表现为间歇性成功/失败。

因此：匿名 Cookie 一旦被 bilibili 风控判定失效，或该 IP 的匿名配额用尽，
**所有** bilibili 路由会同时降级（不是单个 UP 主的问题），这正是
「早上正常、下午不行」以及「其他 UP 主也不行」的原因。

路由级缓存（`lib/middleware/cache.ts`）只缓存**成功**的响应，
失败时不会回吐旧数据；缓存命中的响应带 `RSSHub-Cache-Status: HIT` 头。
并发拉取同一路径超过 `cache.requestTimeout` 会抛
`RequestInProgressError: This path is currently fetching, please come back later!`。

排查手段：在同一实例、同一时刻分别请求两个不同 UID 的路由。
两者都失败 → 共享凭据/风控问题；只有单个失败 → 账号侧问题。

## 补充：本地 Folo 的 Cookie / 浏览器配置位置

用户问「本地启动的 Folo 在哪配 cookie、怎么装浏览器」。查明：

- **本地 Folo 默认连的是官方后端**：`VITE_API_URL` 在
  `packages/internal/shared/src/env.desktop.ts` 中默认取
  `DEFAULT_VALUES.PROD.API_URL = "https://api.folo.is"`
  （见 `packages/internal/shared/src/env.common.ts`）。`apps/desktop/` 下只有
  `.env.example`、没有 `.env`，所以本地前端实际请求 api.folo.is，
  抓取由**官方 RSSHub 实例**完成 → 用户无法为其配置 Cookie。
  `.env.example` 里 `VITE_API_URL=http://localhost:3000` 对应
  `DEFAULT_VALUES.LOCAL.API_URL`，但本仓库不含后端，需另行部署。
- **Cookie 是 RSSHub 侧的环境变量**：`BILIBILI_COOKIE_<UID>=<cookie串>`
  （RSSHub `lib/config.ts` 用 `name.slice(16)` 取 UID 作 key；值含
  SESSDATA / bili_jct / DedeUserID 等）。支持多账号，且
  `getConfiguredCookie()` 是**随机挑一个**。
- **自建实例接入 Folo 的入口**：`/rsshub` 路由
  （`pages/(main)/(layer)/(subview)/rsshub/index.tsx`，
  由 `modules/user/ProfileButton.tsx:203` 的 `navigate("/rsshub")` 进入，
  即右上角头像菜单）。弹窗 `modules/rsshub/add-modal-content.tsx`
  只收 `baseUrl` + `accessKey`，最终调用 `api.rsshub.create`（服务端存储）。
  弹窗里展示的 Folo 专属 env 为 `FOLLOW_OWNER_USER_ID` /
  `FOLLOW_DESCRIPTION` / `FOLLOW_USER_LIMIT`。
- **浏览器安装**：报错 `chromium_headless_shell-1223` 出现在 RSSHub 主机上。
  Docker 用 `diygod/rsshub:chromium-bundled` 标签自带 Chromium；
  手动安装则 `apt install chromium` + 设 `CHROMIUM_EXECUTABLE_PATH`。
  注意 Playwright 库版本与浏览器二进制版本严格绑定。
  但装浏览器只修复回退路径，真正解法仍是配 Cookie 让 API 直连生效。

## 补充：微信公众号如何取得可订阅的 URL

Folo 的 `getWebsiteFeedCandidates()`（`website-feed.ts:76-105`）只识别两种微信 URL：

| URL 形态                          | 要求                                                                       | 生成路由                                          | UI 标签           |
| --------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------- | ----------------- |
| `mp.weixin.qq.com/mp/homepage`    | `__biz` 匹配 `[\w+/=-]+`；`hid` 纯数字；`cid` 可选纯数字（`cid=0` 会保留） | `rsshub://wechat/mp/homepage/{biz}/{hid}[/{cid}]` | 微信 · 公众号栏目 |
| `mp.weixin.qq.com/mp/appmsgalbum` | `__biz` 同上；`album_id` 纯数字                                            | `rsshub://wechat/mp/msgalbum/{biz}/{album_id}`    | 微信 · 公众号合集 |

**文章链接 `mp.weixin.qq.com/s?...` 被明确拒绝**（`website-feed.test.ts:84-94`
的 `does not invent routes` 用例含 `https://mp.weixin.qq.com/s?__biz=abc`），
会回落到通用 HTML 提取，并显示提示文案 `discover.website.notice.wechat`
（`locales/app/zh-CN.json:120`）。

另一条可用路径：发现框**支持直接粘贴完整 `rsshub://` 路由**。
`UnifiedDiscoverForm.tsx:51-60` 的 `detectInputType()` 识别 `rsshub://` 前缀，
经 `rsshubSchema` 校验后直接进 `FeedForm`，跳过网站匹配流程。
RSSHub 的 `lib/routes/wechat/` 下另有 sogou / ershcimi / wechat2rss /
tgchannel / feeddd / uread / ce / data258 / announce 等第三方镜像路由。

预览面板会用 `data-testid="resolved-feed-url"` 显示最终解析出的路由，
可用来确认匹配结果。

## 补充：公众号「能不能订阅」的完整答案

结论：**能订阅，但不能用文章链接，且稳定性依赖第三方**。

可用的四条路径：

1. **合集链接** — 文章顶部「合集」→ 右上角 `...` → 复制链接，
   得到 `mp.weixin.qq.com/mp/appmsgalbum?__biz=...&album_id=...`。
2. **栏目链接** — RSSHub `mp.ts` 的 description 明确写道：
   「只适用拥有首页模板（分享链接带有 homepage）的公众号」，
   例：`https://mp.weixin.qq.com/mp/homepage?__biz=MzA3MDM3NjE5NQ==&hid=4`。
   即**从公众号分享出来的链接**里带 `homepage`。`cid` 为页内栏目，
   最左为 0 向右递增。该路由 `antiCrawler: true`。
3. **在 Folo 里浏览现成路由** — 发现页 `Recommendations()`
   （`modules/discover/recommendations.tsx`）渲染 `RSSHubCategories`
   （`packages/internal/constants/src/rsshub.ts`）分类卡片，
   链接到 `/discover/category/:category`。
   `wechat/mp.ts` 的 `categories: ['new-media']` → 在 **📣 新媒体** 分类下。
4. **第三方镜像** — RSSHub `lib/routes/wechat/namespace.ts` 自述：
   「公众号直接抓取困难，故目前提供几种间接抓取方案，请自行选择」。
   除 `mp/homepage`、`mp/msgalbum` 外还有 sogou / ershcimi / wechat2rss /
   feeddd / tgchannel / uread / ce / data258，按账号名或 id 订阅，
   不需要 `__biz`。可用完整 `rsshub://wechat/...` 直接粘进发现框。

风险：微信无官方开放接口，以上均为非官方方案，第三方服务可能随时关停或收费。

## 补充：关于「去掉计划限制」

用户要求移除 Folo AI 的计划限制、并从设置里删掉所有计划相关内容。查证结果：

- **计划限制是服务端强制的**。`components/ui/ai-summary-card/AISummaryCardBase.tsx:118-119`：
  `shouldSuggestUpgrade = useIsPaymentEnabled() && error instanceof FollowAPIError
? error.status === 402 : undefined`。即升级卡片是**服务端返回 HTTP 402** 触发的，
  改客户端只能改变失败时的展示，无法真正解锁官方云端 AI。
- **BYOK 路径本来就不受计划限制**。`modules/entry-content/use-entry-summary.ts`：
  `official` 的 `enabled: enabled && !provider`，`byok` 的 `enabled: enabled && !!provider`，
  最后 `return { ...(provider ? byok : official), isByok: !!provider }`。
  且 `byok-summary.ts` 直接 `fetch()` 到用户自己的 provider，`credentials: "omit"`，
  完全不经过 Folo 服务端（注释明确写了 provider billing is independent）。
  → **配置 BYOK provider 本身就是绕开计划的正规路径。**
- **仍可能卡住 AI 的是残留的角色判断**（与 BYOK 无关）：
  - `hooks/biz/useEntryActions.tsx:380` — AI 翻译 `disabled: userRole === UserRole.Free || UserRole.Trial`
  - `modules/entry-content/hooks.tsx:53`、`modules/entry-column/item.tsx:30` — `shouldPrefetchTranslation = enableTranslation && !isFreeRole(userRole)`
  - `modules/settings/helper/setting-builder.tsx:96` — `role === UserRole.Free && ...`
  - `modules/discover/FeedForm.tsx:355`、`modules/settings/tabs/general.tsx:305` — `disabledForRole = role === UserRole.Free && isPaymentEnabled`
  - `isFreeRole` 定义在 `packages/internal/constants/src/enums.ts:43-45`

结论：把上述判断改成「未配置 BYOK 时才检查计划」是合理且能生效的改法；
彻底无计划的构建应走自建后端（`useIsPaymentEnabled()` 为 false 时全部计划 UI 自然消失）。

## 深挖：AI 链路到底被什么卡住（用户选「让 AI 对 BYOK 放行」后）

**重要结论：客户端没有针对摘要的角色门禁，用户以为要改的东西本来就是对的。**

- `modules/entry-content/components/AISummary.tsx` 无任何角色判断，
  `enabled` 仅来自 `useShowAISummary()`（general 设置 / entry 设置 / once 状态）。
- `use-entry-summary.ts` 已是 BYOK 优先：`official` 的 `enabled: enabled && !provider`，
  `byok` 的 `enabled: enabled && !!provider`。
- `AISummaryCardBase.tsx:118` 只在服务端 402 时才显示升级卡片。

**真正的门禁是特性开关 `ai`：**
`lib/features.tsx` → `featureConfigMap = { ai: "AI_CHAT_ENABLED" }`，
`hooks/biz/useFeature.ts` 读服务端配置；覆盖它的 UI 入口：
`modules/app/EnvironmentIndicator.tsx` 的 `EnvironmentDebugModalContent`
（右下角徽章 → Debug Actions，**仅 DEV 可点**，显示 `{role}:🐛{MODE}`），
存储为 `atoms/debug-feature.ts` 的 localStorage 键 `follow:debug-feature`，
形如 `{ __override: true, ai: true }`。`useFeature("ai")` 的消费点：
`useEntriesByView.ts:44`、`EntryListHeader.tsx:58`、`ProfileButton.tsx:46`、
`ContainerToc.tsx:51`、`AISummaryCardBase.tsx:114`。

**没有把翻译/对话/时间线改成 BYOK 感知的原因：**
`docs/byok-web.md` 明确「本阶段只实现单篇文章摘要，翻译/对话/时间线摘要保持上游行为」，
且 `packages/internal/store/src/modules/translation/` 内无任何 byok 代码。
放开 `useEntryActions.tsx:380`、`entry-content/hooks.tsx:53` 的角色判断
只会让请求打到服务端拿 402，属于把禁用换成报错，不是修复。
若要这些功能走自带 key，需为其实现 BYOK（功能开发，非去限制）。

## 深挖 2：开了 `ai` 调试开关后，AI 对话发送按钮仍不可点
